## Narrow correction

Only the observer helper and parent capture reader, plus their two tests, changed. Each keeps a private process-lifetime `_UNCERTAIN` map keyed by descriptor, retaining the opened-object identity (device, inode, file type, device number), first cleanup error and first control exception. These private objects do not enter the observation schema or public receipt.

Cleanup uses the existing three query/close slots. A failed identity query consumes a slot and never permits a close. A matching known identity permits close. Successful close or query `EBADF` (Linux errno 9) proves release and retires the entry; other query errors do not. Differing or unknown identity remains recorded and is never closed. A close error alone does not establish release. A transient query error can recover within the same three slots where a known identity is available; the helper can establish its initial identity within that same call. The capture reader conservatively retains a descriptor whose initial ownership query never established an identity, recording that original query error and control before rethrowing it.

The helper latches `write_failed` while any entry remains, carries retained controls into cancellation, writes refusal and revokes the owned healthy observation where possible. Persistent invalidation-lock failure may leave that lock live and prevent a new recorder from proceeding. The registry still records the live descriptor; the failure is reported, not described as cleanup success. Parent capture refuses later healthy observations while any entry remains. Earlier business failure and compiler return facts remain sticky. No compiler invocation or return code is inferred from cleanup failure.

There is no new deadline, recovery API, dependency, field, actor or acceptance waiver. The helper retains its existing eleven-module standard-library grant. Inode identity cannot distinguish a close followed by reopening the same inode; these controls only establish foreign-reuse protection for a different opened object. Persistent faults do not promise descriptor recovery. Explicit fixture teardown happens after measuring live ownership and checks the fixture's exact descriptor identity before closing it; production has no automatic registry-clearing operation.
