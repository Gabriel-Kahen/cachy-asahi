# Repository external authority callbacks

`scripts/ci/development/repository_authority.py` implements two conditional callbacks on the exact captured `RootCallbacks` class: `public_receiver(controller, pending_capture, *, deadline)` and `authority_provider(candidate_path, candidate_sha256, input_root, *, deadline)`. Both return only `{path, sha256}` for original durably written bytes. Import and construction start no actor. There is no default filesystem selection, verifier callback, Docker endpoint, or actor grant.

Construct the object with the exact selected source root, external execution-grant bytes and SHA256, actor-contract bytes, adapter output path, enclosing job deadline, and actual source-authenticated `repository_handoff.Session`. A source-only object without a Session can establish its live binding but refuses both callbacks. The output argument names the enclosing Session output; callback files are created only inside the Session-owned private `handoff-*` directory, which its existing cleanup removes.

`handoff_binding()` returns exactly twelve fields: schema version, purpose `root-repository-handoff-live-binding`, source commit, run ID, run attempt, external execution-grant SHA256, actor-contract SHA256, initial-invocation SHA256, integration-lock SHA256, policy SHA256, license SHA256, and empty supported-model list. The initial invocation is the grant-selected hash of the exact original argv and absolute adapter output. The callback does not invent argv or export private paths. The grant hash is checked against an external selection; it is not embedded as its own hash.

Every callback authenticates its exact class, declared slot descriptors, method descriptors, code filenames, function code, globals, defaults, and approved contextmanager closure cells. Immutable slot state retains source/grant/actor bytes and paths. No subclass, property substituted for a method or state slot, foreign helper namespace, or injected verifier can satisfy these checks. The actual Session/Sources and original Controller classes are separately checked against captured source. Their job, pending identity, private directory, terminal zero exit, original invocation hash, cleanup state, and controller paths must agree with the selected grant and actual `GITHUB_SHA`, `GITHUB_RUN_ID`, and `GITHUB_RUN_ATTEMPT`.

The receiver captures the exact pending file map, retains the original eight-field public manifest hash, and verifies its eleven ordered cases, exact public file set, sizes/hashes, raw evidence crosswalk, four baseline/upgrade archive identities, regular alias copies, strict TEST configuration, public-key armor/signature packet boundaries, and the complete six-field missing-database proof. It checks terminal aggregate/native records before issuing a small closed thirteen-field public receipt. That receipt includes the manifest digest and job identity; it contains no raw files, private paths, context, command arrays, or private keys. This is artifact custody validation; cryptographic acceptance remains a separate issuer predicate.

The issuer captures the candidate and exact private input map once, then copies only those bytes into a fresh mode-0700 private verification tree with mode-0400 files. Only the verification copy changes candidate and crypto statuses from PENDING to PASS. Those statuses supply the existing verifier's required input shape and confer no acceptance by themselves. The issuer reconstructs the actual authenticated runtime/phase modules using the corrected source loader, checks terminal/checkpoint/launch/cleanup facts, and invokes the actual pinned phase gate under the source-bound `RoleSupervisor`. Only its successful natural completion and cleanup permit writing accepted authority bytes. The existing `Session` still independently runs `seal_terminal` and restage afterward.

The phase map remains pinned to `5718ca6c…`, its gate to `c6d37e45…`, and initial integration/policy/license pins to `d4d60314…`, `ff424921…`, and `51a352b3…`. There is no injected verifier parameter or PASS-lambda fallback. Gate verification can run private GPG actors, so it requires the coordinator's actual live execution and actor grants; this author lane runs no GPG, Docker, compiler, installation, or native actor.

All reads are bounded, single-link, nofollow and descriptor-relative. File, ancestor, exact tree, and post-capture identity checks constrain custody. Writes use fresh exact-inode atomic publication and fsync. Cleanup preserves earlier business errors and later cancellation, retries a failed close only while the descriptor still identifies its owned object, and uses the same enclosing deadline rather than renewing time. Ordinary failure and cancellation become sticky callback state. These controls do not establish authenticity against noncooperating same-UID mutation, distinguish a malicious reopen of the exact same inode, or promise recovery from arbitrary persistent filesystem faults.
