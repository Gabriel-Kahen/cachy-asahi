# Separate signed604 fresh installer

Source implementation only. Native604 composition acceptance is UNBOUND and is
the first policy gate in both the coordinator and manual workflow preflight.
No input revisions are emitted, private secrets exposed, output created or
native actor loaded while that gate is unbound. Root alone binds the actual
decision, freezes adopted bytes, publishes and dispatches this lane.

The predecessor is Root-accepted signed600 installer run38965999704 at source
3cbd856315adb30ba7a1b9246739a520c19c9728. Its3332-byte decision is already pinned
through immutable carrier fd42f51b6c32a1cca69df5699760ed2a9e39329f. That acceptance
does not establish a604 transaction.

The unchanged original producer prepares signed587 and its574 builder. The
existing expanded604-composition input reader and materializer select585
unchanged original archives plus19 actual incoming archives, including the
four management packages, Welcome2 and Setup5, giving exactly604. All604
archive/signature pairs use the same two checked public signer roles; eighteen
new signatures use only the producer's existing private ephemeral TEST key,
and the original official LSP signature is retained. This lane builds no new
candidate package pairs.

adapter.py first invokes the byte-pinned accepted600 adapter. A second closed
AST transformation changes only declared function/keyword roles:604 count,
target lock, purpose/status/resource ownership, explicit target package bounds,
and the Setup5 version constraint. Whole AST comparisons reject any undeclared
change. Original600 and587 code, workflows and shared default limits remain
unchanged. The six private generated runners remain individually byte-bound;
the original52 runtime source files remain complete. The separate new source
manifest covers the604 input/materialization helpers and new coordinator too.

The actual full604 fresh ALPM transaction, signature/dependency/conflict checks,
NOHOOKS/NOSCRIPTLET, namespace authority, real lock behavior, ordinary NNP/cap0
parent, numeric IDs and root-owned04110 D-Bus helper metadata, complete payload
and ownership maps, source/cache/user preservation and independent post-parent
root readback all remain required. No nodes or metadata are dropped. The
observer600 backend is embedded byte-identically, with the same statx/fdinfo
cross-check and fallback, full hashing, closed hardlinks and600-second deadline.
Engine4500s, QEMU5400s, VM owner9600s and outer15600s remain held. The only allowed
derived SONAME output remains the original exact declared link. Natural exit,
process retirement and ordered VM/cache/producer cleanup are mandatory.

The coordinator passes the entire signed604 cache to the held VM host. It
retains backing inputs on uncertain VM retirement or public-verifier absence.
Only a matching604 owner receipt authorizes ready604 cleanup. Borrowed caches,
legacy inputs and other owners are never globally retired. The new manual
workflow retains the same nine bounded public reports/tails plus retention
manifest, with4MiB/file and8MiB aggregate bounds.

## Remaining Root bindings

input-policy.json intentionally has status UNBOUND_NATIVE604_ACCEPTANCE. Only
after actual native604 composition passes, Root must publish an immutable
public decision carrier and bind native604.source_sha, run_id, carrier_source,
decision (exact relative path/bytes/SHA256), source_manifest_sha256 and
input_policy_sha256. Set status ROOT_BOUND_NATIVE604_ACCEPTANCE. The decision
must have:

- status ROOT_ACCEPTED_NATIVE_EXPANDED604_COMPOSITION;
- package_count604 and expected604_sha256
  76c37db5eb097662f4a9ca0465680de285466b0443916a50255ea5b8f6d6c946;
- the same source_sha, run_id, source_manifest_sha256 and input_policy_sha256;
- installed_lifecycle, installed_six_modules and cleanup all PASS;
- hardware NOT_RUN and release NOT_ADMITTED.

The two source digests must equal the actual accepted composition manifest and
input policy in the implementation checkout. The carrier revision and both
decision files are checked before secrets. A run number, earlier refused run,
proposed manifest or this lane's synthetic protocol tests cannot fill this gate.

After adoption and actual binding, Root runs freeze.py against the canonical
implementation root. It checks the unchanged604 composition closure, freezes
the finite combined source set, and replaces the new workflow's two explicit
digest markers. Source and workflow commit identities must match. Root must
rebase/freeze against the final accepted604 carrier-path fix; this proposal
does not pin a failed/refused604 trial as accepted. Commit the resulting source
and dispatch only the separate native-arm-expanded604-installer-vm workflow.

## Inert controls

Set EXPANDED604_SOURCE to the implementation repository,
EXPANDED604_LEGACY_ROOT to the byte-exact83-file legacy source checkout, and
EXPANDED604_FRESH600_DECISION to that public carrier's payload/fresh600.json.
Run unittest discovery for this lane's test_*.py. The unchanged600 controls
additionally use EXPANDED600_LEGACY_ROOT and EXPANDED600_SEVEN_ROOT. These tests
are inert source/protocol and private temporary-tree checks. They cannot
authorize main with an unbound real policy. No giant fuzz matrix or new native
actor is part of the controls.

This remains a generic ARM4K software experiment. Physical fresh installation,
macOS/Asahi partition and boot setup, first usable hardware login, hooks and
scriptlets, native-container P0 repair,16K, both M2 Air sizes, service/audio
execution, performance, production trust and release admission remain separate.
