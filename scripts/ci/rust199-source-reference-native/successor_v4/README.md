# V4 native Source checkpoint

This implements a separate six-input dispatch primitive and a two-job hosted
route. It is a **DATA checkpoint**, not a runnable or published Source. LLVM253
has been superseded by a capability-fix successor; its replacement Source pins
and matching independent Reader contract must be rejoined before publication or
any run. Current static LLVM253 evidence remains explicit and acceptance remains
NULL. No Source/ref/run/job, carrier selectors, approval, artifact, Reader result
or Root decision is invented.

The constructor reads the complete exact Rust286 and LLVM253 trees as local
DATA, checks bytes, modes, membership, Git trees and Source maps, then overlays
the new finite code and records a whole inverse to Rust286. All older
constructors, profiles and outputs remain untouched. Candidate source, intake,
recipe and compiler flags are protected byte for byte. The archived independent
Reader is not imported or executed by construction or tests.

The six workflow inputs are `source_sha`, `source_map_sha256`,
`approval_sha256`, `root_admission_sha256`, `root_admission_json` and `operation`.
Only compact canonical Root JSON has a 16-KiB UTF-8 allowance; the other five
strings retain the 200-character limit. The review digest and raw admission
digest are distinct. Original9d is not changed. The new primitive requires a
separately sealed Root custody runtime; it does not supply lease acquisition or
an operational CLI. It retains same-FD/PIDFD/independent nonblocking custody,
Source readback, Main CAS, one pair of five-status EMPTY sweeps and exactly one
POST. Ambiguity, incomplete discovery or an uncertain POST produces HOLD with
no retry. No dispatch has occurred.

Root grants the exact Source/ref/map, resources, material selectors and once
budget while future Rust run/job IDs stay NULL. Both phases verify the closed
Source and manual attempt1 environment. Each derives its real running job ID
from REST inside the workflow. Actual bootstrap/build bindings and native
qualification are carried as separate readonly proof files; the raw Root grant
is preserved. Root source/legal review and LLVM acceptance remain external.

The bootstrap job uses the preserved signed349 helper and original retained200
transport, the existing private22/public14 seed mechanism, a separately selected
LLVM Original, a retained approximately108-MB stage0 carrier, and a separate Root
proof/signature carrier. Rust and LLVM source archives use exact pinned HTTPS
URLs, bytes and hashes. Artifact metadata, successful producing job, Source,
run, selected members and whole archive hashes must match before use. API
credentials do not follow redirects; only exact Root-provided Azure blob hosts
are allowed. Acquisition has finite request/body/time limits and no fallback.

The qualified image installs the accepted public-TEST-signed private LLVM
package with offline ALPM into a real private prefix. A scoped host GPG home
verifies the signature; no private signing key or production trust is created.
Rootfs export is bounded, extracted as DATA, and checked by tree digest.
Qualification uses an exact CHOWN-only initializer followed by cap0 actors,
all with nocopy, no network, readonly root, no-new-privileges and fixed cgroup
limits. Stage0 assembly performs no compiler build. All nine original runtime
probes and actual EROFS attempts on both readonly stage0 aliases must succeed.
Cargo metadata is not rewritten to satisfy a runtime probe.

The same workflow transfers selected readonly materials and raw proofs plus a
Docker image archive to its build job. The transfer pins the compact Root grant,
actual bootstrap job, immutable image and all member hashes. The importer checks
the entire membership before Docker load, requires absent target image/tag,
checks exact Source ownership labels and image ID, and can restore only the
previously absent deterministic owned tag. The bootstrap rootfs path remains
historical evidence; it is not represented as a current build-host directory.
The build uses the same qualified immutable image and unchanged prepare/main
actors. Exact ownership and retirement are required after failures as well as
successes; foreign resources are never removed.

`resource-policy.json` proposes two jobs under the existing `native-arm-build`
concurrency group, queue max, cancellation false: bootstrap 246 minutes and
build 360 minutes, with 606 aggregate job minutes. Each phase separately budgets
its inner actor/volume cleanup and final image retirement. Image load is nested
within the transfer ceiling. It preserves the main actor's 16,200-second ceiling. The
12-GiB image/16-GiB phase artifact transfer is a separate bounded path; it does
not widen the original material fetch cap. Docker28 metadata may spell the
single initializer capability `CHOWN` or `CAP_CHOWN`; duplicates, extras and
unknown capabilities refuse. Actual kernel effective/permitted/bounding masks
must still equal1. No seven-cap actor lifecycle is added here.

Run every listed test in its own isolated Python process; several tests install
permanent audit fences. `ci-routing.json` describes the portable commands for
Python 3.12/3.14. Whole-tree construction and inverse checks are separate local
DATA observations in `validation.json`. Mocked acquisition, transfer and native
receipt controls do not demonstrate downloads, Docker execution, successful
qualification, compilation, installation or hardware operation. Native 16K/M2,
performance, source/license completeness, production trust and release holds
remain open.
